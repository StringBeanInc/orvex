# Temporarily closed public company registration

On firebase-preparation, `VITE_ENABLE_PUBLIC_SIGNUP` defaults to false unless its build-time value is exactly `true`. `.env.example` records the default. `/account` opens Sign In; creation links, registration fields, and new-company setup actions are hidden. Routes, query strings, localStorage and window variables cannot toggle the compiled flag. Login, persistent sessions, email verification, password reset, and existing company directories remain available. Registration code is retained.

The flag is a presentation control, not authorization. Firestore's trusted gate is `platformConfig/publicSignup.enabled`. Bootstrap requires this record to exist and contain boolean true; missing or false fails closed. Clients may read this nonsecret boolean but cannot write it. The current demo-orvex emulator gate is explicitly false, and local rules enforce it across the company, Owner membership, owner employee and user lookup atomic bootstrap. Changing frontend code or bypassing the UI cannot create a company or grant membership while the server gate is closed. Existing company reads and Customers/Properties writes do not depend on the signup gate.

Reopening requires a deliberate administrator action on the server gate and `VITE_ENABLE_PUBLIC_SIGNUP=true` followed by restarting/rebuilding Vite. Neither switch alone reopens the normal application flow. No production settings or rules have been changed or deployed.

## Firebase Auth limitation

Firestore Rules cannot reject calls to Firebase Authentication's own signup API. With the email/password provider enabled, a caller may still create an Auth identity directly. That identity receives no ORVEX company or membership and cannot access company data; an automated test verifies this exact bypass attempt is rejected at Firestore. Do not describe this change as disabling every Auth identity creation endpoint.

Identity Platform documents a provider-level `client.permissions.disabledUserSignup` control that can block end-user account creation across API methods. Review availability/configuration and test login preservation before applying it to a real project; it was not changed here. A beforeCreate blocking function is another option requiring Identity Platform and a deployment/service review. Do not disable the entire email/password provider as a signup workaround, since existing users need it for login. No provider upgrade, billed service, or production deployment was performed. See [Identity Platform configuration](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/Config) and [blocking functions](https://firebase.google.com/docs/auth/extend-with-blocking-functions).

## Tests

The normal application uses localhost:5173, demo-orvex, and a closed server gate. Enabled-registration regression tests run on a separate localhost:5174 test server with the UI flag explicitly true and Firestore project demo-orvex-auth-tests with its own open test gate. The Auth emulator serves SDK requests using its existing demo-orvex Auth project, so tests use unique synthetic identities and never clear existing Auth users. Test teardown closes the separate test server gate again. The test server must be stopped after testing; it is not the normal application. Only two hard-coded demo Firestore project IDs are permitted by the development adapter; production initialization remains disabled.

`npm run test:signup-disabled` verifies hidden signup, URL/window/localStorage manipulation, a direct verified Auth identity failing the complete Firestore bootstrap, denied client gate changes, preserved existing login/customer persistence and unchanged local business bytes. Rule tests verify both missing and false gates deny bootstrap while existing memberships still read their company. `npm run test:auth` retains the enabled signup/auth/CRUD regressions in the separate test environment. Local backup, recycle-bin and business persistence code remains separate.
